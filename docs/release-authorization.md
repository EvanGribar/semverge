# Gate 2 release authorization

Gate 2 evaluates eligibility for one operation, promoting a specific Vercel Preview deployment to Production. The evaluator is an internal Cloud module with no HTTP, MCP, or CLI route. The migration and evaluator are exercised against an isolated PostgreSQL-compatible fixture. The Gate 1 JSON journal remains deployment history and supplies no authorization inputs.

## Decision and trust boundary

- A PostgreSQL record binds a server-issued authorization ID to a workspace, GitHub repository ID, release branch, full commit SHA, workflow and configuration blob IDs, CI run and attempt, evidence timestamp, Vercel team, project and immutable Preview deployment ID, target environment, operation, approver GitHub ID, decision, issue time, and expiry. The database enforces unique authorization IDs and at most one terminal event per ID. The current workspace repository binding must still match.
- The server must authenticate the caller, resolve the workspace and repository binding, and provide its own database connection and fresh provider readers before calling the evaluator. The request supplies only the candidate and target identifiers. The Vercel reader must issue a fresh team-scoped HTTPS GET for the exact deployment ID with Git repository info. GitHub reads use the trusted workflow and repository checks in the existing CI evidence adapter.
- The evaluator requires that the Preview is ready, proves GitHub provenance for the authorized SHA, and has a current, passing CI attempt that exactly matches the approved evidence revision. It reads the database again after provider I/O to catch expiry, revocation, consumption, and loss of the active repository binding. An approval for commit A can no longer qualify when the release branch points to B. Submitting B under A's authorization ID also fails.
- PostgreSQL is the trust anchor. A future issuer must authenticate and authorize the human approver and derive all approval fields from server-verified facts. The evaluator needs a dedicated read-only database identity. Issuance and terminal events need separate trusted writers with insert-only access to their respective tables. Keep app code, agents, and ordinary Cloud database credentials outside that write boundary. Database owners and administrators remain trusted. Protect database access and backups, and explicitly revoke outstanding authorizations on binding or approver offboarding. The fixture verifies the reader's privileges locally. Hosted roles and issuance are separate work.
- An allowed decision is a point-in-time read. It can be repeated while the record remains eligible. The unique terminal record blocks reuse of a consumed ID. Before executing an operation, a future broker must revalidate the bound inputs, atomically claim the authorization and persist an operation record under a unique idempotency key, then dispatch the pinned deployment ID. It must reconcile an ambiguous provider response against that operation record before any retry. GitHub, PostgreSQL and Vercel cannot share a transaction. Define the final head check as the decision time, and never resolve the operation's deployment or source from a moving branch after that check. A stronger guarantee that the branch cannot move before dispatch would require independent control over ref updates.

## Vercel paths outside the evaluator

| Path | What the isolated fixture must demonstrate before claiming enforcement |
| --- | --- |
| Git-connected deployment and automatic domain assignment | A push or merge alone cannot create a production deployment or move production traffic within the operation's claimed scope. Verify the actual project settings and a push with no approval. Git-connected Vercel projects can deploy automatically from their production branch. [Vercel Git deployments](https://vercel.com/docs/git) |
| Dashboard, CLI, API, CI credentials, deploy hooks, and integration identities | The agent principal and its reachable credentials cannot deploy, promote, redeploy, or trigger a hook that affects Production. Inventory CI workflows, integrations and project access in addition to the human dashboard roles. Verify denied attempts under representative fixture identities. [Vercel roles](https://vercel.com/docs/rbac/access-roles) · [Vercel deployment management](https://vercel.com/docs/deployments/managing-deployments) |
| Aliases, rollback, rolling releases, and project changes | Only trusted identities can move production traffic or change branch, project, credential, or domain settings. Record any administrative break-glass path and its audit trail. [Vercel promotion controls](https://vercel.com/docs/deployments/promoting-a-deployment) |
| Approvals, CI policy, and deployment provenance | The requesting agent cannot write approval rows or terminal history, replace the evaluator, tamper with the trusted workflow policy, or supply provider responses. Verify that a CI rerun, evidence loss, and altered or locally fabricated provenance fail closed. |

Vercel's Preview-to-Production flow can start a separate build with production environment variables. A future broker must correlate the resulting immutable production deployment to the operation and independently verify repository, SHA, readiness, production-domain routing, and health. Gate 1 only established source provenance for the observed Preview deployments. [Vercel Preview promotion guide](https://vercel.com/docs/deployments/promote-preview-to-production)

Proof of exclusive control remains open until an isolated fixture shows the direct paths are closed or explicitly governed. Gate 2 makes no provider write calls and applies no hosted permission or database changes.
